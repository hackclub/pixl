# Airbridge-first fulfillment verification (V2)

## Purpose
Replace the unreliable bulk Ships API with targeted Airbridge reads of individual Unified approval records. The fulfillment page reads *only PostgreSQL*, never Airtable, Otter, Airbridge, or Ships. The syncing route is independent and authenticated.

## Architecture
- `FULFILLMENT_SHIPS_SOURCE=airbridge`: opt-in provider. Unset retains the existing Ships path.
- `fulfillment_unified_cache` in migration `0236` holds the latest staging->Unified mapping and verified approval (only public fields).
- `fulfillment_unified_changes` is append-only audit history generated by a database trigger when record identity, hours, status or Slack identity changes.
- `fulfillment_unified_sync_lease` prevents overlapping reconciliation workers across dashboard replicas.
- The background job fetches staging mapping with Pixl's existing private Airtable token, then does **bounded server-side Airbridge record-ID queries** of up to 25 at a time.
- Otter is enrichment only. Its Slack ID is accepted only if it returns an exact matching Unified record ID **and** exact normalized repository and YSWS. It can veto a mismatched identity, never establish approval by itself.
- Each approval has a verified timestamp. Older than 30 minutes means unavailable, not approved. A successful "not found" removes verification only after independently checking the absent ID. Network failures do not silently refresh timestamps.
- Refresh fairness uses last attempted time, independent from verification time, so persistent failures cannot starve healthy records. Bad Airbridge batches do not invalidate successful batches.
- Conflicting staging→Unified mappings are rejected even if one of the mappings has no current approval.
- Otter distinguishes a negative match from a network outage. If previously known Slack identity disappears, a sticky identity-review flag blocks approval until a fresh exact Otter match; no known identity can silently degrade into a permissive null. The database UPSERT preserves this block across temporarily missing staging records and approvals. No match for a record that never had Otter identity remains optional under the existing exact staging-ID/repository trust model.
- No currency or shop-order writes. Existing payout, commitment, and grant checks remain in force.

## Local verification
- Fulfillment-staff-only **read-only** diagnostic page `/fulfillment/airbridge-preview` shows the real cache and per-record status without affecting the live funding verifier or any claim, payout or order action. Use this to test warm-up while the legacy verifier remains active.
- `/fulfillment` uses `shipsProvider().get()` which performs only local Postgres reads. Sync health is computed across the **full active approved owner/collaborator staging cohort** (including not-yet-cached records), and reports current, unsynced, stale, failed and identity-review counts. The newest approval's timestamp is only shown as *latest update*, never as whole-cohort freshness.
- `loadPlayerEvidence` fetches staging->Unified mappings from Postgres when Airbridge is enabled, not the staging API.
- On claim, eligibility is re-evaluated against the local cache and existing fulfillment ledger. **The existing claim enforcement policy has not been changed by this PR.**

## Scheduled reconciliation
GET `/api/cron/fulfillment-airbridge`, authenticated by dashboard `CRON_SECRET`. It can populate the local read model **before** `FULFILLMENT_SHIPS_SOURCE=airbridge` is enabled; the cron's authentication, not the reader flag, gates reconciliation. It synchronizes up to 60 least-recently-attempted staging records per invocation. Run every **5 minutes** with an Orchard scheduled Job, passing the credential securely. The old Ships GitHub scheduled workflow remains disabled.

### Production cutover checklist (must complete before enabling the flag)
1. Apply migration 0236 through the standard Pixl migration process; verify the cache tables and audit trigger exist.
2. Configure a secure scheduler credential and Orchard Job; avoid committing secrets to GitHub.
3. Run the worker repeatedly until it has covered all approved owners and collaborators and inspect errors/stale records.
4. Compare Airbridge records and funding verdicts against the current path on real orders **read-only**, especially fines, removals, reships, and collaborations. Investigate discrepancies with Pixl organizers.
5. Confirm the job never silently truncates data, API rate limits are acceptable, and local evidence freshness meets the 30-minute funding policy.
6. Set `FULFILLMENT_SHIPS_SOURCE=airbridge` on the dashboard deployment. Keep rollback: unset the flag to restore the existing Ships provider. Do not remove legacy schema yet.
7. Monitor latency, invalid mappings, missing approvals, and claim/fulfillment corrections; do not automate negative clawbacks until financially reviewed.

## Limits
Airbridge's public allowlisted fields do not include Slack identity; trusted staging mapping plus repo identifies the record, with optional Otter cross-check. Missing Otter identity does not automatically block an otherwise exact mapped record; team should confirm that trust model. The public Approved Projects table may temporarily omit a fine-affected row: absence triggers manual review rather than an automatic reversal. A YSWS-level HCB fine must be reconciled against the **program budget**, not automatically deducted from a player's hours.

The Otter Slack enrichment is checked at most once every 12 hours after a completed lookup. Transient Otter failures preserve a previously verified matching Slack ID without extending its enrichment-check timestamp. A negative response after a previously observed ID requires manual review rather than silently permitting record-only verification.
